## 1. Goal

Restructure the terminal frontend so that a small **kernel** owns the terminal
runtime, the frame, and the shared state, and every UI surface (the file tree,
the source view, the overlays, and the diff views) is a **plugin** written
against one contract.

Deliverables:

1. Three crates replace `crates/tui`:
   - `tui-core`: the kernel, the plugin API, and the design system.
   - `tui`: the built-in plugins, the plugin registry, and the public `run`.
   - `tui-diff`: the compare (range) and history (commits) views, behind the
     default-on `diff` feature of `tui`.
2. `tui-core` never names a plugin: no plugin type, plugin ID, or plugin module
   appears in it. Built-in and optional plugins use only `tui-core`'s public
   API.
3. User-visible behaviour is unchanged except for the intentional changes in
   section 6.2.
4. `crates/cli` source is unchanged. It still calls
   `tui::run(engine, tui::TuiOptions { request, scope_label, icons })`.
   (Phase 6 changes this only if it is signed off; see section 14.)
5. The architecture docs describe the new structure (section 11).

Phase 6 (activating views at runtime, so the explorer is always present) is
specified but **gated on product sign-off**. Phases 0–5 deliver the structure
without changing the session model.

### 2.1 What is kernel, built-in plugin, and optional plugin

The rule:

- **Kernel:** holds state and shared services, and draws only the frame.
- **Built-in plugin:** anything that draws content. Always compiled in.
- **Optional plugin:** anything that adds a new data source. Feature-gated.

The kernel is Codect-specific, not domain-neutral: it owns
`Workspace { query: Query { mode, scope }, files, selected, search }` (section
4.6), so `available_modes`, `mode_label`, `BadgeTone`, and the search model live
in `tui-core`. "Kernel names no plugin" is a structural rule; it is not a claim
that the kernel is a reusable code-explorer host.

| Piece | Verdict | Crate |
|---|---|---|
| Runtime: terminal lifecycle, event loop, input batching, panic hook | Kernel | `tui-core` |
| Effect scheduling: running plugin effects, busy frame, after-batch hook | Kernel | `tui-core` |
| Layout host: Navigator / Body / Band placements, dividers, resize | Kernel | `tui-core` |
| Focus ring and mouse hit-testing | Kernel | `tui-core` |

### 2.2 Mechanism

- **Compile-time plugins only.** No dynamic loading, no scripting, no `dyn
  Plugin`, no `Any`. The kernel is generic over `S: PluginSet`. The registry is
  a struct generated by the `plugin_set!` macro, with one field per plugin and
  one message and effect enum variant per plugin.
  - Why: the model is plain `Clone` data replaced wholesale by `update`.
    Tests compare the returned effects (`Cmd`) with `==` and inspect the model
    field-wise; whole-model `==` is not derived, and plugin messages are compared
    with `matches!`, because a message may carry a `Box<EngineError>` and
    `EngineError` is not `PartialEq`. Static dispatch keeps both. It also keeps
    the read-only and never-executes-repository-code invariants trivially true.
- **Plugins never call each other.** They talk only through kernel state
  (`Cx`), kernel `Request`s, and kernel `Event`s.
- **Compare and history are two views of one plugin type** (`DiffPlugin` in
  `tui-diff`). They share base, target, merge-base, and the diff pane, and
  switching between them is internal to the plugin, as it is today.
- **One overlay slot**, as today. Prompts become overlays owned by the prompt
  plugin.
- **The kernel owns the committed query** (mode and scope), the file set, the
  selection, and the search. A view owns its revision(s) and the data it loaded.
- **Registration order is behaviour.** Events are broadcast in registration
  order (section 4.7). The order is fixed in section 4.5.

### 2.3 Session model

Until Phase 6 is signed off, a session still starts in exactly one view: the
source view for `tui show`, and the compare or history view for `tui diff`.
Range and commits still switch within the diff plugin. The kernel supports
`ActivateView` from Phase 4 on. Phase 6 only adds commands that use it across
plugins.

### 2.4 Extension model

Plugins are **compile-time and in-tree**. `tui-core` exposes `Plugin`,
`PluginSet`, `Request`, and `Event` as an unstable internal contract: adding a
shipped surface means editing `crates/tui/src/registry.rs`, and adding a new
kernel capability means adding a `Request` or `Event` variant in `tui-core`. A
third party may depend on `tui-core` and build its own `PluginSet` and binary,
but it cannot reuse the built-in plugins (they live in `tui`, which is not a
composition library) and it inherits no stability guarantee. Runtime plugins —
dynamic libraries, scripting, user-editable keymaps — are a non-goal (section
13); the registry only makes them possible later. This work is a structural
separation, not a plugin platform.

### 3.2 Flow today

The TUI follows The Elm Architecture (TECHNICAL_DESIGN §21.2):

1. `lib.rs::run_with` draws, reads one event, folds queued events into a batch
   (≤256 events, ≤8 ms), and calls `update` once per message.
2. `update(msg, &App) -> (App, Vec<Cmd>)` clones the app and mutates the clone.
3. `coalesce_commit_loads` adds at most one `Cmd::Step` for the commits view.
4. `settle` computes highlighting, search re-sync, and the diff row layout.
5. If there are effects, the busy frame is drawn first. Then each `Cmd` runs
   through `interpret(&Engine, Cmd) -> Msg`, and the result goes back through
   `update`.

### 4.4 The plugin contract

```rust
// tui-core/src/plugin.rs (sketch)

#[derive(Clone, Copy, Debug, Eq, PartialEq, Ord, PartialOrd, Hash)]
pub struct PluginId(pub &'static str);           // "kernel" is reserved

#[derive(Clone, Copy, Debug, Eq, PartialEq, Hash)]
pub struct PaneId { pub owner: PluginId, pub slot: u8 }
#[derive(Clone, Copy, Debug, Eq, PartialEq, Hash)]
pub struct FocusKey { pub owner: PluginId, pub slot: u8 }
#[derive(Clone, Copy, Debug, Eq, PartialEq, Hash)]
pub struct ViewId { pub owner: PluginId, pub slot: u8 }

/// An uninhabited message or effect type for plugins that have none.
#[derive(Clone, Debug, Eq, PartialEq)]
pub enum Never {}

pub trait Plugin: Clone + 'static {
    const ID: PluginId;
    type Msg: std::fmt::Debug;
    type Cmd: Clone + std::fmt::Debug + PartialEq;

    // Declarations: pure reads. `cx.commands()` and `cx.layout*()` are empty
    // while the kernel is collecting these, so never read them here.
    fn panes(&self, cx: &Cx) -> Vec<PaneSpec> { Vec::new() }
    fn commands(&self, cx: &Cx) -> Vec<CommandSpec> { Vec::new() }
    fn help(&self, cx: &Cx) -> Vec<HelpEntry> { Vec::new() }
    fn hints(&self, target: HintTarget, cx: &Cx) -> Option<&'static str> { None }
    fn chips(&self, cx: &Cx) -> Vec<Chip> { Vec::new() }        // active view only
    fn status(&self, cx: &Cx) -> Vec<Segment> { Vec::new() }    // active view only
    fn overlay_spec(&self, pane: PaneId) -> OverlaySpec { OverlaySpec::MODAL }
    fn busy(&self) -> bool { false }

    // Drawing: pure.
    fn render(&self, pane: PaneId, geometry: PaneGeometry, focused: bool,
              cx: &Cx, frame: &mut Frame) {}
    fn render_overlay(&self, pane: PaneId, area: Rect, cx: &Cx, frame: &mut Frame) {}

    // Reactions: mutate only `self`; talk to the world through `Out`.
    fn input(&mut self, pane: PaneId, input: Input, cx: &Cx) -> Reply<Self::Cmd> {
        Reply::unhandled()
    }
    fn run(&mut self, command: CommandId, cx: &Cx) -> Vec<Out<Self::Cmd>> { Vec::new() }
    fn update(&mut self, msg: Self::Msg, cx: &Cx) -> Vec<Out<Self::Cmd>> { Vec::new() }
    fn on_event(&mut self, event: &Event, cx: &Cx) -> Vec<Out<Self::Cmd>> { Vec::new() }
    fn search(&mut self, needle: &str, cx: &Cx) -> Vec<SearchMatch> { Vec::new() }
    fn after_batch(&mut self, pending: &[Self::Cmd], cx: &Cx) -> Vec<Out<Self::Cmd>> {
        Vec::new()
    }
    fn settle(&mut self, cx: &Cx) {}

    // Effects: only the runtime calls these.
    fn perform(engine: &Engine, cmd: Self::Cmd) -> Self::Msg;
    fn startup_failure(msg: Self::Msg) -> Result<Self::Msg, Box<EngineError>> { Ok(msg) }
}

pub enum Out<C> {
    Effect(C),
    Kernel(Request),
}

pub struct Reply<C> {
    pub handled: bool,
    pub outs: Vec<Out<C>>,
}

pub enum HintTarget { Focus(FocusKey), Overlay(PaneId) }

#[derive(Clone, Copy)]
pub struct OverlaySpec {
    /// Printable keys go to the overlay, so `q` does not quit.
    pub captures_text: bool,
    /// Keys the overlay does not handle are swallowed instead of falling through.
    pub modal: bool,
    /// Ctrl-J / Ctrl-K reach the overlay as themselves instead of `j` / `k`.
    pub keeps_ctrl_jk: bool,
}

pub enum Input {
    Key(Key),
    Nav(Nav),          // Top, Bottom, PageUp, PageDown — from kernel commands
    Mouse(MouseInput),
}

pub struct MouseInput {
    pub kind: MouseKind,
    pub column: u16,
    pub row: u16,
    pub geometry: PaneGeometry,   // the pane the event hit, as drawn
}
```

Contract rules for plugin authors (put these in `tui-core`'s crate docs):

1. `render`, `render_overlay`, `panes`, `commands`, `help`, `hints`, `chips`,
   `status`, `overlay_spec`, and `busy` are pure and cheap. No I/O. No caching
   through interior mutability.
2. `input`, `run`, `update`, `on_event`, `search`, `after_batch`, and `settle`
   mutate only `self`. Engine work leaves as `Out::Effect`. Everything else
   leaves as `Out::Kernel(Request)`.
3. `perform` is the only place that touches the `Engine`, and only the runtime
   calls it.
4. A plugin reads other plugins' state only through `Cx`.
5. Every `PaneId`, `FocusKey`, `ViewId`, and `CommandId` a plugin creates uses
   `Self::ID` as its owner. The kernel `debug_assert!`s this.
6. An unhandled `Input::Key(Key::Esc)` must return `handled: false`, so the
   kernel default (clear the diagnostic and the search) runs.
7. The kernel attributes an `input` reply's `Out::Kernel(Request)` to the owner
   of the pane the input was routed to (the open overlay's owner while an
   overlay is open), and a `run` reply's requests to the invoked command's
   owner. `Request::OpenPrompt` therefore carries no `from` field; the kernel
   fills `Event::PromptRequested { from }` with that owner.

### 4.5 `PluginSet` and the registry macro

```rust

    fn hints(&self, target: HintTarget, cx: &Cx) -> Option<&'static str>; // routed by owner
    fn chips(&self, cx: &Cx) -> Vec<Chip>;         // routed to the active view's owner
    fn status(&self, cx: &Cx) -> Vec<Segment>;     // routed to the active view's owner

    fn render(&self, pane: PaneId, g: PaneGeometry, focused: bool, cx: &Cx, f: &mut Frame);
```

### 4.7 One update step, requests, and event routing

`update(msg, &app)`:

1. Clone the app.
2. Collect `panes`, `commands`, and `help` from `plugins` with a bootstrap `Cx`
   (empty specs), then build the real `Cx` that holds them.
3. Dispatch the message:
   - `Key`: section 4.8.
   - `Mouse`: section 4.9.
   - `Resize`: set the size, then broadcast `Event::Resized`.
   - `Tick`: advance the spinner and age the diagnostic, as today.
   - `Plugin(m)`: `plugins.update(m, &cx)`.
4. Process the resulting outs. Effects are appended to the returned `Vec<S::Cmd>`
   in order. Requests go to `apply_request`.
5. **Depth-first with cached specs.** `panes`, `commands`, and `help` are
   collected once in step 2 and cached for the whole step; the `Cx` for each
   request is rebuilt from kernel state but borrows that cache, so a request
   cascade never re-collects them. Requests produced while applying a request
   are applied immediately after it, before its next sibling. `ActivateView`
   changes the active view and therefore the visible declarations, so the kernel
   re-collects once after it. Every other declaration-affecting change is a
   plugin message in a later step, and step 2 re-collects before that step's
   dispatch and before each draw; a plugin message is not re-collected within its
   own step, which is safe because a plugin's declarations never gate its own
   handling of that message. Collections are per step, never per request. The
   depth limit is 16; on overflow the kernel sets the diagnostic directly on
   `Kernel` (not through the request queue) and drops the remaining requests.
   Exceeding the limit in a `debug_assertions` build is a bug (`debug_assert!`).
6. **Focus normalisation.** At the end of the step, if `focus` names no
   `FocusKey` among the current panes, apply `FocusDefault`.

`apply_request` semantics (kernel state is the truth; events tell plugins):

| Request | Kernel does | Then broadcasts / routes |
|---|---|---|
| `Quit` | `quit = true` | — |
| `Diagnose(t)` | set the diagnostic (ttl 40) | — |
| `ClearDiagnostic` | clear it | — |
| `SetFiles(set)` | replace `files`; if `selected` is not in `set.paths`, set it to `None` (no event) | `FilesChanged` (all) |
| `Select(p)` | `selected = p`; clear the pending prefix (as `select_path` does today) | `PrefixCleared` if one was pending; `SelectionChanged` (all) |
| `Requery(c)` | nothing | `Requery(c)` → the active view's owner |
| `QueryLoaded(q)` | `query = q` | `QueryChanged` (all) |
| `SetSearch(n)` | empty `n` → `search = None`; else matches = `plugins.search(active owner, n)`, cursor 0 | `SearchChanged` (all) |
| `CommitSearch` | — | `RevealMatch(current)` → owner, if there is a current match |
| `ClearSearch` | `search = None` | `SearchChanged` |
| `Focus(f)` / `FocusDefault` / `CycleFocus` | update `focus` (section 4.11) | — |
| `ResizeNavigator(r)` | clamp 15–60, step 5, reset 30 | — |
| `OpenOverlay(p)` | if another overlay is open, replace it | `OverlayClosed(old)` → its owner |
| `CloseOverlay(p)` | close it if it is `p` | — |
| `OpenPrompt{..}` | — | `PromptRequested { from: <the pane owner the input came from, or the invoked command's owner>, .. }` (all; the prompt plugin acts) |
| `SubmitPrompt{to, ..}` | — | `PromptSubmitted` → `to` |
| `CancelPrefix` | clear `pending` if set | `PrefixCleared` (all) if it was set |
| `RunCommand(id)` | kernel-owned id → run it; else `plugins.run(id)` | — |
| `ActivateView(v)` | `active_view = v`; `search = None` | `ViewActivated(v)` (all), `SearchChanged` |

`n`/`N` (kernel commands): advance the search cursor with wrap-around, as in
`advance_search`, then send `RevealMatch(current)` to its owner.

### 4.8 Key dispatch (exact)

This reproduces `app.rs::handle_key` order. The numbered steps are normative.

```text
dispatch_key(k):
 1. k == Ctrl-C                                   → Quit; stop.
 2. If no overlay is open, or the open overlay's spec has keeps_ctrl_jk == false:
        Ctrl-K → Char('k'), Ctrl-J → Char('j').
 3. If an overlay O is open (spec = overlay_spec(O)):
        a. k == Char('q') and !spec.captures_text → Quit; stop.
        b. reply = owner(O).input(O, Key(k)); apply reply.outs.
        c. reply.handled or spec.modal            → stop.
 4. If keymap.pending == Some(p):
        CancelPrefix.
        If k == Char(c) and a binding Prefixed(p, c) is in scope → RunCommand(id).
        Stop.
 5. k == Char('q')                                → Quit; stop.
 6. If k == Char(c) and some binding Prefixed(c, _) is in scope:
        pending = Some(c); broadcast PrefixPending(c); stop.
 7. If a binding Key(k) is in scope               → RunCommand(id); stop.
 8. If focus == Some(f): reply = owner(f).input(first pane with focus f, Key(k));
        apply reply.outs; if reply.handled → stop.
 9. k == Esc                                      → ClearDiagnostic; ClearSearch.
```

"In scope" means `KeyScope::Anywhere`, or `KeyScope::Focused(f)` with
`focus == Some(f)`.

Registry validation (`keymap.rs`, run in `debug_assertions` builds on every
collection and in a unit test over the real registry):

- No two in-scope commands bind the same `KeySeq`.
- No character is both a `Key(Char(c))` binding and a `Prefixed(c, _)` prefix
  in overlapping scopes.
- Every `Prefixed` binding has a `group`.

Kernel-owned commands (owner `PluginId("kernel")`):

| Id name | Label | Hint | Bindings | Palette | Rank | Does |
|---|---|---|---|---|---:|---|
| `quit` | Quit | `q` | (step 5 and Ctrl-C handle the keys) | yes | 390 | `Quit` |
| `pane.next` | Switch pane | `Tab` | `Tab` | yes | 320 | `CycleFocus{forward: true}` |
| `pane.previous` | — | — | `BackTab` | no | — | `CycleFocus{forward: false}` |
| `nav.top` | Jump to top | `g` | `g`, `Home` | yes | 360 | `Input::Nav(Top)` → focused pane |
| `nav.bottom` | Jump to bottom | `G` | `G`, `End` | yes | 370 | `Input::Nav(Bottom)` → focused pane |
| `nav.page_up` | — | — | `PageUp`, `Ctrl-U` | no | — | `Input::Nav(PageUp)` → focused pane |
| `nav.page_down` | — | — | `PageDown`, `Ctrl-D` | no | — | `Input::Nav(PageDown)` → focused pane |
| `search.next` | — | — | `n` | no | — | advance and reveal |
| `search.previous` | — | — | `N` | no | — | retreat and reveal |

`q` stays out of the binding table because step 5 must sit after prefix
resolution. The `quit` command exists so the palette can list and run it.

### 4.9 Mouse dispatch (exact)

```text
dispatch_mouse(m):
 1. CancelPrefix (no-op if none pending).
 2. If an overlay is open, or width < 40, or height < 8 → stop.
 3. layout = cx.layout(); slot = first slot whose outer contains (m.column, m.row);
    none → stop.
 4. focus = slot.focus.
 5. owner(slot.pane).input(slot.pane, Mouse(MouseInput { kind, column, row,
    geometry: slot.geometry })); apply outs.
```

Plugins reproduce today's per-pane rules exactly (section 5): tree index
arithmetic without an inner check, the commit band's inner check on click,
the source body's inner check and gutter width, and diff panes scrolling on the
wheel only.

### 4.10 Layout (exact, preserving `render/layout.rs::body_layout`)

Inputs: the content rect (`frame_areas`), `navigator_percent`, the visible
`PaneSpec`s, and a focus. Visible specs are: every `Navigator` pane, plus the
`Body` and `Band` panes of the active view's owner.

- `SINGLE_PANE_MIN_WIDTH = 40`, `MIN_HEIGHT = 8`,
  `SIDE_BY_SIDE_MIN_WIDTH = 80`, `COMMITS_BAND_MAX_HEIGHT = 9` (rename it
  `BAND_MAX_HEIGHT`), `BODY_MIN_HEIGHT = 3`. Values unchanged.
- If any `Band` pane is visible, split it off the bottom first with
  `split_band(content)`, which is today's `split_commits_band`. The band slot
  is `Edge::Solo`. Band panes stack in registration order (today: one).
- **Narrow** (`width < 80`), on the strip above any band:
  - If focus is a navigator's `FocusKey`: one navigator slot, `Edge::Solo`.
  - Otherwise: the body panes stacked vertically in equal percentages, each
    `Edge::Solo`. One body pane takes the whole strip.
  - No dividers.
- **Wide** (`width ≥ 80`): columns are `[navigator?] ++ body panes`. The
  weights are `[navigator_percent]` followed by `rest = 100 - navigator_percent`
  split evenly: each body pane gets `rest / n` and the last gets the remainder.
  Then `split_with_dividers`, and edges from `edge_for(index, last)`.
- `PaneGeometry.inner` is `pane_block("", false, theme, edge).inner(outer)`.
  That block function lives in the kernel library.
- `body_visible` (used by settle): not too small, and
  (`width ≥ 80` or focus is not a navigator focus).

Existing tests in `render/layout.rs` (lines 520+) move to `tui-core` and are
rewritten with fake pane specs. The rects they assert stay identical.

### 4.11 Focus ring

- The ring is the distinct `FocusKey`s of the visible specs, ordered
  `Band…`, then `Navigator…`, then `Body…`. Within a placement, registration
  order, then first appearance.
- `CycleFocus { forward }` moves to the next or previous key, wrapping. (This
  changes `Tab` in the source view; see section 6.2.)
- `FocusDefault` picks the first `Navigator` focus, else the first `Body`
  focus.
- Initial focus is `FocusDefault`. The history view requests its band's focus
  when its history loads.

### 4.12 Settle

`settle(app)`:

1. Build `Cx`.
2. `plugins.settle(&cx)` in registration order. Views compute visible rows,
   highlighting (only if `cx.body_visible()`), and the diff row layout. The
   tree fits its viewport.
3. Kernel search re-sync. If `search` is set, recompute its matches with
   `plugins.search(active owner, needle)` and clamp the cursor to
   `len - 1`, saturating.

This preserves today's order: rows → highlight → search re-sync → diff rows,
then the tree viewport. Diff rows do not depend on search, and the tree does
not depend on either.

### 4.13 Effects and the runtime

`tui_core::run::<S>(engine, kernel_options, plugins, startup: Vec<S::Cmd>)`
keeps today's loop exactly, with these substitutions:

- `interpret(&engine, cmd)` becomes `S::perform(&engine, cmd)`, wrapped as
  `Msg::Plugin`.
- Startup: draw once, then perform each startup command in order. If
  `S::startup_failure(msg)` returns `Err(e)`, return `TuiError::Engine(*e)`
  with the terminal restored (today's `run_with` behaviour). Otherwise fold the
  message with `update`.
- After folding a batch: `plugins.after_batch(&cmds, &cx)`, which replaces
  `coalesce_commit_loads`. Then `settle`, the busy frame if there are effects,
  and the effects in order, each result folded back with `update`.
- The idle-tick skip (`Tick` while not busy and no diagnostic) is unchanged.
- `Theme::detect()` still runs in `run` before the first event poll.
- `Driver`, `Session`, `CrosstermDriver`, `MouseCaptured`, `translate`,
  `translate_mouse`, and the panic hook move unchanged. The `Driver` trait's
  `draw` takes `&App<S>`.

`tui::run(engine, TuiOptions)` keeps its signature. It builds
`(Plugins, startup cmds, kernel options)` from the `LoadRequest` and calls
`tui_core::run`.

### 4.14 Rendering and chrome

`view(app, frame)` (normative order, as `view/mod.rs` today):

1. Paint the whole area with `palette.bg`.
2. Too small (`width < 40` or `height < 8`): render "terminal too small", then
   the overlay if one is open; stop.
3. `frame_areas` → header, content, status.
4. Header: the brand, the root clipped from the left (≤ 40 columns), then
   chips `[mode (Accent)] ++ active view chips ++ [scope: <label> (Neutral)]`,
   dropping chips from the right while they don't fit, with today's widths.
5. Body: for each slot in `cx.layout()`, call
   `plugins.render(slot.pane, slot.geometry, focused, &cx, frame)`, where
   `focused` is `focus == Some(slot.focus)`. Then draw the dividers.
6. Status: spinner and `projecting… ` when busy; the selected path or
   `no selection`; the active view's `status` segments; the search segment
   `/<needle≤20> <i>/<n> ` when a search is set; then the hints, right-aligned,
   with the compact and empty fallbacks at today's width thresholds.
   - Hints: with an overlay open, `hints(Overlay(o))`. Otherwise
     `hints(Focus(f))`.
   - Compact hints: `"Esc close "` when an overlay is open, else `"? help "`.
7. Diagnostic toast.
8. The overlay, if any: `plugins.render_overlay(o, area, &cx, frame)`.

Tone mapping:

- `ChipTone::Accent` → `palette.accent`; `Neutral` → `palette.surface_alt`.
- `SegmentTone::Muted` → `text_muted`; `Added` → `add_fg`; `Removed` →
  `del_fg`; `Text` → `text`.
- The search segment uses `match_fg`.

Each subsection lists the plugin's ID, state, panes, commands, help rows,

### 5.1 `tree` — file tree (`crates/tui/src/tree/`)

- **ID** `PluginId("tree")`. Pane `PaneId(tree, 0)`, placement `Navigator`,
  focus `FocusKey(tree, 0)`.
- **State** today's `component::tree::Tree` (`collapsed`, `rows`, `cursor`,
  `scroll`, `viewport`) and `build_rows`.
- **Render** today's `tree::render` / `tree_line` with:
  - selection from `cx.workspace.selected`;
  - badges from `cx.workspace.files.badges` (`Added`→`"A"`/`badge_add`,
    `Modified`→`"M"`/`badge_mod`, `Deleted`→`"D"`/`badge_del`);
  - the empty state `("Loading", "Projecting files…")` when `cx.busy`, else
    `cx.workspace.files.empty` (tree only);
  - icons from `cx.icons`.
- **Input**
  - Keys: `↓`/`j` Move(1), `↑`/`k` Move(-1), `→`/`l` Open, `←`/`h` Close,
    `Enter` Toggle. All other keys are unhandled.
  - `Nav`: Top→ToTop, Bottom→ToBottom, PageUp/PageDown→Page(∓step) with
    `step = page_step(cx.size.height)`.
  - Mouse:
    - Click: `index = scroll + (row - inner.y)` (saturating); if
      `index < rows.len()`, Click(index).
    - Wheel: Scroll(∓3).
  - Every `OutMsg::Selected(p)` becomes `Request::Select(Some(p))`.
  - The viewport height for every operation is
    `cx.layout_if_focused(FocusKey(tree,0))`'s inner height for this pane
    (today's `tree_viewport_height`).
- **Events**
  - `FilesChanged`. This is today's selection fallback, normative:
    ```text
    hint = cursor (before sync)
    sync(&cx.workspace.files.paths)
    match cx.workspace.selected:
      Some(p) → reveal(p, viewport)
    ```

## 6. Behaviour

### 6.1 Must not change

Each item is covered by an existing test or a golden frame. If a task breaks
one, the task is wrong.

- Every key binding, palette label, hint, and palette order (section 5).
- Which-key: `z` with the source body focused opens the band. A binding key
  runs it. `↑`/`↓`/Ctrl-K/Ctrl-J/`Enter` navigate and run. Any other key,
  `Esc`, a mouse event, or a reload closes it. `q` closes it and does not quit.
- Ctrl-J/Ctrl-K act as `j`/`k` everywhere except inside the band. Inside a
  text-capturing overlay that means they type `j`/`k`, as today.
- `q` quits unless a text-capturing overlay is open. It quits from help and
  from the mode picker.
- `Esc` with no overlay clears the diagnostic and the search.
- The selection after a reload: the previous selection if it is still
  visible, else the nearest visible file at or after the tree cursor, else the
  last file, else none. The body resets to the top on every load.
- Any tree move onto a file, `Enter` on a file, a finder pick, or a click
  resets the body, even when the path is unchanged.
- Fold overrides are sticky across a reload and a selection change.
- Failed reloads keep the previous state and show a 40-tick diagnostic.
- The busy frame is drawn before effects run. A burst of input is one frame.
  Commit navigation in one batch loads only the final step.
- Layout geometry at every width and height, the commit band cap, and the
  responsive thresholds.
- Mouse: tree click and wheel arithmetic; commit band click; source gutter
  toggle at columns `< 2` of `inner`; diff wheel; header and divider clicks do
  nothing; mouse is ignored while an overlay is open.
- Theme, `NO_COLOR`, icons, and the opaque canvas.
- `codect tui …` flags, exit codes, and diagnostics. The `cli` tests in
  `crates/cli/tests/tui.rs` and `pty.rs` pass unchanged.
- Read-only: no plugin writes the repository.

Only these may change test expectations or golden frames, and only in the
listed task. Each is listed in the task's PR description.

## 12. Risks

| Risk | Mitigation |
|---|---|
| Subtle ordering changes (selection fallback, body resets, prefix clearing, busy state) | Sections 4.7–4.8 and 5.x make the orders normative; golden frames and the 134 app tests are the oracle; depth-first requests keep causality |
| Event broadcast order becomes hidden coupling | Registration order is fixed in section 4.5 and documented; a plugin may rely on an event's kernel state, never on another plugin having already reacted |
| Generic and macro noise; compile time | One `macro_rules!` fan-out; plugins are plain types; measure `cargo build -p tui` time before and after Phase 4 and note it in the 4.10 PR |
| Per-step collection of panes and commands costs frames | Collect once per update step and once per draw; bench guard at four checkpoints |
| `Legacy` grows instead of shrinking | Each 4.x task must delete code from `Legacy`; reviewers reject a 4.x PR that adds to it |
| White-box tests churn | `test_support.rs` absorbs path changes; test bodies change only for listed intentional changes |
| The viewport approximation (`height − 4`) used by page scrolling is wrong with a band | Preserved on purpose; fixing it changes behaviour. File a follow-up after Phase 5 |
| Diff widths drift when `side_widths` is replaced | Width sweep test against the old formula before deletion (task 3.1) |
| Kernel overreach (kernel learning about folds, diffs, or commits) | The acceptance grep (section 10) and review; kernel types talk about panes, views, commands, files, and selection only |

## 13. Non-goals

- Runtime plugins (dynamic libraries, Lua, WASM) and user-configurable keymaps.
  The registry makes them possible later; they are not part of this work.
- New features, except Phase 6 if signed off.
- Changes to `base`, `git`, `engine`, the language crates, or CLI output.
- Fixing the page viewport approximation (section 12).
- Theme or visual changes beyond the intentional changes in section 6.2.
- Async work, threads, or persistent caches.

## 15. Glossary

- **Kernel** — `tui-core`'s state and services: runtime, frame, workspace,
  keymap, overlay slot, focus, layout.
- **Plugin** — a type implementing `Plugin`; declares panes, commands, help,
  hints, chips, and status, and reacts to input, commands, events, and effect
  results.
- **View** — a plugin-provided body (source, compare, history). Exactly one is
  active.
- **Pane** — a laid-out region with a `Placement` (`Navigator`, `Body`,
  `Band`). Overlays are not panes in the layout; they occupy the overlay slot.
- **Focus key** — the unit `Tab` moves between. Several panes may share one
  (the diff's Old and New sides).
- **Request** — a plugin's instruction to the kernel.
- **Event** — the kernel's notification to plugins.
- **Effect / Cmd** — engine work a plugin describes and the runtime performs.
- **Registry** — the `plugin_set!`-generated `Plugins` struct in `tui`.
